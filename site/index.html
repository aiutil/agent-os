让 Agent 工作从一次回答，变成可以延续的系统

运行位置、审阅证据和长期积累属于同一条工作链。Agent OS 把它们留在一个可追踪、可搜索、由人控制的工作台中。

01 / RUN

在正确的位置运行

为每项工作选择本机或授权远程 Runtime Host，并明确 CLI、模型、工作目录、权限和会话策略。

  • 结构化 Agent 会话与原生 CLI 终端共存
  • 一次任务、计划任务与 Cron 使用相同运行配置
  • 远程节点的能力与目录由受托管端批准并可撤销
02 / REVIEW

依据运行记录与证据审阅

不只接收最后一段答案。按运行批次查看执行事件、失败与重试、可用的交付物和关联会话，再由人确认 Done。

  • Todo、In Progress、Review、Done 四阶段任务流
  • 每次尝试保留独立运行记录；最终回复可用时进入交付物审阅
  • Web、CLI 与多个 Agent 可并排比较
03 / CONTINUITY

把有价值的工作留下来

短小信息进入分层记忆并按作用域召回；体系化成果成为带主题、标签和来源的 Markdown 知识文章。

  • 记忆与知识职责分离，避免长文章污染 Agent 上下文
  • 知识支持草稿、发布、收藏、本机评论与全文搜索
  • 图谱与列表共享搜索、筛选和阅读脉络

四类重度 AI 用户，四种持续工作流

Agent OS 不替代模型或 CLI。它解决的是高频使用之后出现的管理问题：上下文分散、任务无法追踪、自动化不可靠，以及不同机器之间缺少统一入口。

01 · 独立开发者 / 多仓库维护者

十几个终端，不应该承担项目管理

场景
一天内在多个仓库切换，用 Claude、Codex 或 Pi 分别处理开发、排障和文档。
原来的问题
终端标题、工作目录和上下文散落；中断后很难找回“这个 Agent 当时做到哪一步”。
Agent OS
把 Runtime Host、CLI、模型和工作目录绑定到会话与任务，并通过历史搜索、看板和运行记录继续工作。
02 · 技术负责人 / 架构与评审

不只看答案，还要知道它怎么交付

场景
把架构分析、重构建议、测试检查交给不同 Agent，再由自己做最终判断。
原来的问题
只有一段最终输出时，很难核对运行配置、执行批次和失败重试，也缺少明确的验收关口。
Agent OS
每次运行保留过程事件；最终回复可用时进入交付物审阅。结果统一进入 Review，检查关联会话后再确认 Done。
03 · 自动化维护者 / 本地 DevOps

重复工作，不应依赖记得点一下

场景
每天检查异常、每周生成报告、定期扫描依赖或回顾未完成事项。
原来的问题
零散脚本和系统 Cron 缺少 Agent 上下文、执行记录与人工审阅；桌面窗口关闭后也容易担心任务中断。
Agent OS
使用单次计划或 Cron、时区与错过策略；Runtime daemon 持有计划，同一工作目录串行执行并保留结果。
04 · 多设备用户 / 个人工作室

离开主电脑，也能把工作交给正确机器

场景
笔记本负责控制，台式机或家中服务器负责运行；外出时从已授权的消息通道发起工作。
原来的问题
反复远程登录、复制提示词和确认环境；节点版本、CLI 状态与任务结果分散在不同机器。
Agent OS
受托管主机自行批准能力与目录；连接受支持的消息渠道后，用 /use 把工作交给正确 Agent，切换时不覆盖原会话。

不是再做一个聊天框，而是补齐 Agent 工作的操作系统层

重度使用的问题通常不在“能不能问一次”，而在如何同时观察不同界面、找回跨 Agent 上下文、持续执行任务，并对最终结果保留控制权。Agent OS 的功能围绕这条工作链设计。

01 / COMPARE

把 Web、CLI 与 Agent 放在同一张工作台

对比不只发生在模型回答之间。一个面板可以是真实网页，另一个是结构化 Agent 会话或原生 CLI；既能单独输入，也能向多个面板批量发送同一问题。

解决的痛点

减少在浏览器、终端和聊天窗口之间反复复制信息，也能同时观察资料、命令输出和 Agent 处理结果。

02 / STORAGE

跨 Agent 会话搜索与记忆，属于同一存储层

会话历史不按单一厂商割裂。支持来源的会话在本机建立索引，搜索结果可以回到原上下文；经验、候选记忆和记忆策略也在同一存储区域管理。

解决的痛点

不再分别翻找 Claude、Codex、Pi 等工具的历史记录，也避免每次切换 Agent 都重新解释项目背景。

03 / TASKS

把一次提示变成可追踪、可验收的工作

任务经过 Todo、In Progress、Review、Done，保存执行环境、运行批次和过程事件；最终回复可用时进入交付物审阅，计划任务还可按单次时间或 Cron 由 Runtime daemon 触发。

解决的痛点

Agent 运行不再是终端里的一次性输出；重复工作有计划，失败和重试可追溯，最终结果由人确认后才完成。

04 / RUNTIME

跨主机运行，不跨越对方的授权边界

受托管端核验设备并决定开放哪些能力、Agent 与目录；控制端只能看到和使用授权范围内的资源。暂停或撤销后，已有远程访问立即停止。

解决的痛点

把任务交给台式机或服务器执行，同时不要求对方开放整机、根目录或无边界权限。

05 / CHANNELS

一个消息入口，切换已安装且支持结构化聊天的 Agent

飞书等渠道接入一次后，可用 /agents 查看实时可用列表，用 /use codex 等命令切换 Agent。每个 Agent 的会话独立保留，切回时继续原上下文。

解决的痛点

无需为 Claude、Codex、Gemini 等分别搭机器人，也不会因 Agent 切换丢掉上一段对话与记忆。

06 / CONTROL

保留 CLI 原生能力，也保留人的最终控制

同一入口同时提供结构化会话和原生 PTY，不替代厂商 CLI 的登录与能力。任务明确记录权限和会话策略，结果先进入 Review，而不是自动宣告完成。

解决的痛点

避免桌面封装牺牲 CLI 能力，也避免长时间自动化在没有权限边界和人工验收的情况下持续运行。

从选择运行环境到完成验收

任务从看板或消息渠道进入，使用统一的 Runtime Host、CLI、模型与工作目录配置。每次运行保留独立过程记录，最终回复可用时进入交付物审阅，并在 Review 等待人工确认。

01 / CONFIGURE

配置执行环境

选择本机或远程 Runtime Host，并指定 Engineer、模型、工作目录、权限与会话策略。

02 / DISPATCH

派发或计划任务

从看板创建任务，也可使用已授权消息通道转交工作；支持立即执行、单次计划和 Cron。

03 / OBSERVE

查看运行过程

按运行批次查看触发方式、执行阶段与输出事件；多次运行保留在同一任务的历史记录中。

04 / REVIEW

审阅结果

执行结束后进入 Review。检查可用的最终回复或打开关联会话，确认后再标记 Done。
